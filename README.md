# 과제 8 — 비밀번호 없는 개인 자료실 (카드 1~4)

**결과물:** https://my-intro-t08.vercel.app/  
**소스:** https://github.com/dfdfewqk/my-intro-passkey-t08  
**1번 소개 페이지 원본:** https://dfdfewqk.github.io/my-intro-page/

과제 8은 1번 저장소와 분리된 독립 프로젝트입니다. 1번 공개 소개는 iframe/링크로 누구나 볼 수 있고, 연습용 비공개 메모 3건은 클라이언트의 정적 HTML에 넣지 않았습니다.

## 카드별 진행 상태

- **카드 1:** 공개/비공개 UI 분리, 서버 비공개 API의 미인증 요청 HTTP 401 확인
- **카드 2:** WebAuthn 패스키 `horse` 실제 등록 완료, COSE 공개키 서버 저장 확인, 일회용 challenge와 취소 검증
- **카드 3:** 등록된 공개키 서명 확인 후에만 세션 생성, HttpOnly 쿠키, 세션 유효성 조회 후 비공개 메모 반환, 로그아웃 시 서버 세션 폐기. **실제 패스키 로그인 및 실서비스 로그아웃 DB 세션 폐기 확인 완료. 동일 세션 HTTP 401 응답 캡처는 별도 증거 권장**
- **카드 4:** 로그인한 소유자의 두 번째 패스키 등록·이름/날짜 목록·개별 삭제·마지막 키 삭제 방지 구현, 자동/비인증 검증 통과. **실물 두 번째 패스키 등록·삭제·재로그인 검증 대기**
- **카드 5:** 아직 과제 안내를 받지 않아 구현 전

## 구현 파일

- `index.html`: 공개 소개/잠긴 자료실/패스키 로그인 버튼, 보안 검증 화면
- `client/enroll.js`, `api/enroll.js`: 카드 2 등록 화면 및 서버 API
- `client/login.js`, `api/auth.js`: 카드 3 로그인, 질문 두 번 비교, 서명 실패·재사용 테스트, 세션 및 로그아웃
- `api/private.js`: 서명 검증 후 발급한 **현재 유효한 서버 세션**을 확인한 뒤 서버 전용 자료 응답
- `supabase/functions/t08-register/index.ts`: 카드 2 서버 WebAuthn 등록
- `supabase/functions/t08-login/index.ts`: 카드 3 서버 WebAuthn 공개키 서명 검증 및 세션 관리
- `api/keys.js`, `client/keys.js`, `supabase/functions/t08-keys/index.ts`: 카드 4 추가 패스키 등록·관리·서버 삭제 보호
- `test/*.test.mjs`: 자동화된 보안/기능 테스트

상세 증거는 [CARD2.md](CARD2.md), [CARD3.md](CARD3.md), [CARD4.md](CARD4.md)를 확인하세요.

## 보안 요약

- 비밀번호 입력/저장 **없음**, 기기 개인키 전송 **없음**
- 인증 challenge는 데이터베이스에 보관했다가 한 번 소비한 후 삭제
- 암호학적 서명 검증 `verifyAuthenticationResponse()`이 성공해야만 세션 발급
- 12시간 서버 세션, DB에는 불투명 토큰의 **해시만 저장**
- 브라우저 쿠키: `__Host-t08_session` / `HttpOnly` / `Secure` / `SameSite=Strict` (값은 기록/제출 금지)
- 로그아웃 시 DB 폐기 + 쿠키 삭제 + 같은 토큰 재검증
- 모든 비공개 조회는 세션을 매번 서버에서 재확인하고, 미인증/위조 쿠키는 HTTP 401
- 비공개 자료는 Vercel 서버 전용 `T08_PRIVATE_NOTES_JSON`에 보관된 **가상 데이터**
- 과제 증거에는 세션·쿠키·초대 토큰 원문/실제 개인정보를 넣지 않음

## 카드 4 추가 패스키 로그인 화면 통합 수정 (2026-10-20)

- 오류 원인: 카드 2의 소진된 최초 등록 양식이 카드 4 앞에 남아 있었고, 카드 4에서 비로그인 상태의 등록 버튼이 비활성화되어도 같은 자리에서 로그인할 방법이 없었습니다.
- 해결: 카드 4에 **기존 패스키로 로그인하고 계속하기** 버튼을 추가하고, 인증이 끝나면 같은 자리에서 등록 입력란과 버튼이 활성화되도록 바꿨습니다.
- 이미 완료된 카드 2 최초 등록 양식은 숨기고 자료는 CARD2.md로 유지했습니다.
- 비동기 로그인/목록 응답 순서가 뒤바뀌어도 마지막 상태만 화면에 적용하고, 로그아웃/세션 만료 시 이미 표시한 비공개 내용을 잠급니다.
- 추가 테스트: 카드 4 UI 자동 테스트 5건을 포함한 **37/37 통과**; 실제 배포 HTTP 200, 비로그인 관리 요청 HTTP 401, 타 출처 HTTP 403 검증.
- 미완료: 실제 소유자 기기의 두 번째 WebAuthn 등록 및 추가 키 로그인/삭제/복구 시나리오.

**실행 방법:** [카드 4 추가 등록 화면](https://my-intro-t08.vercel.app/#manageKeysPanel) → 1단계 **기존 패스키로 로그인하고 계속하기** → 기기에서 등록한 `horse` 인증 → 2단계 새 이름·저장 위치 선택 → **패스키 추가 등록**.

## 카드 4 추가 등록 상시 개방 수정 (2026-10-20)

기존 문제: 카드 4의 입력칸과 Add 버튼을 로그인 상태에 직접 연결하여, 로그아웃이나 로그인 취소 시 아무것도 누르지 못했습니다. 로그인은 원칙적으로 WebAuthn challenge 검증을 통과해야 하므로, 등록을 무인증으로 허용하는 방식은 사용하지 않았습니다.

**수정 후 동작:** `#manageKeysPanel`에서 추가할 패스키의 이름과 실제 저장 위치를 **로그인 전에도 자유롭게 설정**합니다. `패스키 추가 등록` 클릭 시 서버에서 세션을 확인하고, 유효하지 않으면 기존 패스키 WebAuthn 로그인을 먼저 요청합니다. 성공하면 같은 요청 흐름으로 등록 challenge를 발급해 기기 패스키 생성을 시작합니다. 실패/취소 시 입력 내용은 유지되고 다시 누를 수 있습니다. 등록 중에는 중복 클릭을 막되 취소는 가능합니다. 서버의 공개키 검증과 인증 접근 정책은 그대로 유지합니다.

- 같은 페이지의 `기존 패스키로 로그인하고 계속하기`는 편의용 선택 버튼이며 Add 이용 전 필수 조작이 아닙니다.
- 카드 2 최초 등록 양식은 기존 패스키가 하나라도 등록된 경우 비표시.
- 등록 관련 버튼은 처음 페이지를 열 때부터 사용 가능하며 로그인 여부만으로 비활성화되지 않음.
- 사후 목록은 인증된 세션만 조회 가능하고 마지막 패스키는 삭제 보호됨.
- `npm test`: **37/37 통과** (실제 브라우저 인증 대신 모의 WebAuthn 성공/취소, 세션 만료, 경쟁 조건 및 기존 API 보안 회귀 포함).
- 배포 HTTP 200, 클라이언트 스크립트 로딩 200, 미인증 관리 API `list/options/verify/remove` HTTP 401, 부적절한 Origin 403, 비공개 조회 401 확인.
- 소유자의 **실제 두 번째 패스키 생성/삭제/재로그인 검증은 아직 완료되지 않음**. 기기 인증과 새 키 실제 저장은 사용자가 Windows/브라우저에서 진행해야 함.


## 카드 4 Google 비밀번호 관리자 / Windows Hello / 물리 보안 키 선택 개선

- 원인: 사용자 선택 `storageProvider`가 등록 질문 `options` 요청에 전달되지 않아 Chrome이 기존 Google 비밀번호 관리자를 계속 선택할 수 있었습니다.
- 수정: 서버 발급 WebAuthn challenge의 `authenticatorSelection.authenticatorAttachment`와 `hints`에 모드를 반영. Google은 브라우저 선택, `device`는 `platform` + `client-device`, `security_key`는 `cross-platform` + `security-key`를 요청합니다.
- `excludeCredentials`와 기존 공개키·세션 인증·일회용 challenge 검증은 유지합니다. 선택한 모드는 서버 DB의 challenge와 연결되며 다른 모드로 변경된 verify 요청은 거절됩니다.
- Chrome이 특정 Google 계정, USB 장치까지 정확히 사용하도록 웹사이트가 강제할 수 있는 것은 아닙니다. `hints`는 브라우저가 무시할 수 있으며 `cross-platform`에는 다른 기기 인증도 포함될 수 있습니다.
- 브라우저가 `InvalidStateError`를 반환하면 기존 등록된 인증기 중복이라고 구체적으로 안내합니다. 기존 `horse` 패스키는 절대 제거하지 않습니다.
- `npm test` **37/37 통과**, 배포 화면 200, 기존 보안 API 비인증 요청 401 검증. 실제 기기에서 새 공개키 1개가 생성될지는 사용자 인증 창 확인이 필요합니다.
